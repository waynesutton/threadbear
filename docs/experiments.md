New features that are still being tried out start off, with a switch under
`experiments` in `runner.json` (the user guide, "Experiments", says how to turn one
on). These are the ones there are now.

## What each one does

<!-- list:start -->
- **Schedule checks** (`scheduleChecks`, since 6 Nov 2026). A schedule can have a check: a shell command that runs first, in its folder, each time it's due. If the check prints nothing, that run is skipped and no agent starts, so a schedule that looks for new Sentry issues every five minutes only uses a login when there's something to look at. What it prints is added to the message. If the check itself fails, the run goes ahead with the error, so you hear about it. A check has a minute to finish, or up to five if its schedule says so, for one that reads something slow like Slack. What a check prints is kept until a run carrying it has been sent, so a runner restart in between doesn't lose it. Ask a thread to "only run when there's something new" and it writes the check. Run now skips it. It's bound to what it runs: if a script it reaches changes, it doesn't run until the same check is passed to the schedule again, and the thread is told once.
- **Loose ends on the done card** (`looseEnds`, since 7 Nov 2026). When a thread finishes with nothing for you to do, Threadbear checks what's still open before you archive it: commits on its worktree's branch that aren't on main, files in its worktree that aren't committed, threads it started that are still working or waiting for you, and check-ins it booked. If there's nothing, the done card shows just Done, so Archive is safe without asking the agent first. If there is, it lists them under "Still open" (a thread opens from its line; Land is the chip above the message box). A check-in alone shows under "Coming back", as the thread comes back by itself when it runs. It checks again when you open the thread, after an action like Land, and when a thread it started finishes. The phone's done card doesn't show it yet.
- **Reply buttons** (`replyButtons`, since 7 Nov 2026). An agent can put buttons partway through its reply, beside the line they're about, so you can set jobs off as you read without typing: one starts a new thread with a brief the agent wrote ("Fill in the form"), another sends a message to a thread that's already going. Hover over a button to see the brief and where it runs. Nothing happens until you press it, and it only runs once: after that it turns green and opens the thread it started. It works the same on your phone and the website. A thread without Full access can't make a button that does more than it could itself, and that's checked again when you press it.
- **Standing instructions** (`standingInstructions`, since 7 Nov 2026). An Instructions box in Settings > General, for what every agent should always keep in mind: who you are, how you like things written, what you build with. Every new session gets it, on every login, Claude and Codex alike, and a chat that's already going hears a change before your next message, with a line in the thread saying so. It saves as you type; empty is none. A login's own `CLAUDE.md` or `AGENTS.md` still applies, and is the place for what's particular to that login or provider: this is for what goes for all of them, without keeping several files in step. Only what you save in Settings counts. If anything else changes the file (an agent, say), no agent is given it, Threadbear warns you, and the box shows what the file holds so you can keep it or clear it. Agents can't change this for you, so ask one to draft them and paste it in yourself. On Full access an agent that goes after the runner's own key could still get past this, as it could with anything on your Mac.
- **Voice mode** (`voiceMode`, since 7 Nov 2026). A waveform button beside Send in the Mac app, to talk with a thread out loud and have its replies read out ("Talking with a thread" in the guide). It lives in the app, which reads the switch when it connects to the runner, so turning it on or off takes effect when the app next connects (quit and reopen it). While it's off there's no button and no Voice tab in Settings, nothing downloads and macOS never asks for the microphone. With it on, Settings > Voice > Use with Notes (off by default) adds a waveform button to Notes for talking into a note ("Notes" in the guide).
- **Connectors setup** (`connectorsSetup`, since 8 Nov 2026). Puts the Connectors panel (the plug on the left-hand rail) in reach before there's a gateway, with a Set up button. Set up starts a thread that installs plugbear on this Mac, listening only on 127.0.0.1, and wires each of your logins to it. Once it's running, Add a service lists services it can add (Notion, Slack, Linear, Sentry, Cloudflare, DeepWiki) and takes any other MCP server by its https address. Each Add starts a short thread that adds it to plugbear and hands you its Connect button. Slack needs a Slack app of your own, and that thread walks you through it. Sign-ins and tokens stay in plugbear, never in Threadbear.
- **Local connectors** (`localConnectors`, since 8 Nov 2026). Lets the Connectors panel add MCP servers that run on this Mac as a command, not just ones on the web. Blender is in Add a service, marked On this Mac, and Other local server takes any uvx or npx package at one exact version. Before anything is added, a sheet shows the exact command that will run and which of its tools ask you first (Blender's run-any-code tool always does). The gateway (plugbear) runs the command whenever it's running, and every login and Codex gets its tools, the same as Notion's. A local server has nothing to sign in to, so its row has no Connect button. It needs Connectors setup on too.
- **Move to another machine** (`moveToRunner`, since 8 Nov 2026). A thread moves to another of your machines whole: the same thread, with its whole conversation, its pictures and Highlights, and the git work in its own worktree (commits and uncommitted changes alike). It waits for the turn it's on to end. In the Mac app its message box and any open card are locked until it lands or you cancel; a message sent from your phone meanwhile goes with it. Its next message carries on in the same Claude session on the other machine. If anything goes wrong before it lands, it stays where it was and says why. Its schedules come too, but not a schedule's shell check or the thread's "Always allow" answers: those were given on the other machine, so set them again on the new one. A thread moved to your main Mac from another machine arrives asking before tools run, even if it had Full access or Auto there; give it more access again if you want. Right-click a thread (or use its **...** menu) and pick **Move to**, then the machine. Offline ones are greyed. It goes straight away, to the folder and login that machine guesses. If it can't go, or something won't come (background jobs, changes in a checkout other threads share), a small window shows the folder and login with why; change either and it checks again, then press **Move**. The row says "Moving to" with a spinner until it's gone, then the thread is listed under the other machine, in the same place and still open. If it can't move, the row says so for a minute, with why in its tooltip. Agents can do the same with `move_thread` and a `runner` (a word in two machines' names isn't guessed between: they're asked to say which), and `tb move <thread> --to <machine>` (`--preview` to see where it would go). Moves are started from your first Mac. It needs Threadbear's backend, and the experiment on in both machines' runners; the app shows the menu from the next time it connects after the switch is turned on.
- **Outside agents** (`outsideAgents`, since 8 Nov 2026). Keys allowed to read all can also list and read published Prints. These tools return public metadata and bounded HTML as data, with no write tools. Unpublished Prints stay on the Mac. Unpublish ends access on the next read. Lets an agent that runs in the cloud, such as Grok Bot or a Notion Custom Agent, use Threadbear as an MCP server. In the Connectors panel, Connect an agent lets you pick Grok Bot, Notion or Slack, says what each needs, makes a key for it and shows the server address (your backend's `/mcp`). Slack can't take a key yet (Slackbot only connects to servers that sign in with OAuth), so it says so instead. A read-only key can list and read threads it started, or every live thread if you tick that. A key that can write can also start threads, which always run in Ask mode so every tool asks you first, and message the threads it started while they stay in Ask mode. It never sees approvals, secrets, schedules or archived threads. Messages from it say who sent them, so threads don't take them as yours. Revoke ends a key on its next call, and turning this off ends every key.
- **ACP agents** (`acpAgents`, since 9 Nov 2026). Agent CLIs that speak the Agent Client Protocol get threads of their own, next to Claude and Codex: OpenCode (free models work with no login) and Cursor (after `agent login`). If one is installed it turns up as a login and a pool, and its models in the picker. Everything the agent wants to do comes through Threadbear first: on Ask and Plan first you get the usual cards, Auto behaves like Ask, and Full access goes ahead without them. A folder's own OpenCode config and plugins aren't read in these threads. Cursor can't be told to always ask, so its Ask, Auto and Plan first threads run in its read-only modes and can't change anything; to let Cursor change files, use Full access. Small jobs (titles and summaries) stay on Claude unless you pick a pool of only OpenCode logins for them in Settings. No usage readings, sandbox or going back to an earlier message for these yet, and Threadbear only updates their CLIs when you press Update in the Updates panel.
- **Card reviewer** (`cardReviewer`, since 9 Nov 2026). In a thread on Auto, when something would stop for your OK (an edit to a file Threadbear runs as code, a message to a thread with more access, anything else that puts up an approval card), a reviewer looks at it first: Opus, with no tools, shown the card in full and what the thread was asked to do. If it fits the task and can't do real harm, it goes ahead, and the transcript says "Allowed by the reviewer" with its reason. If the reviewer has doubts, or can't run (no pool, a private folder, a card too long to read whole), the card comes to you as before, after a note with its reason. The reviewer is told that everything it reads is data, and that text trying to tell it what to answer is a reason to hand the card to you. Cards that hand out access lasting past the one action (switching a thread to more access, starting a thread with more, a schedule, moving a thread or changing its logins) always come to you. Codex threads' own tool cards come to you too, as they name the files a change touches but not the change. Ask before edits, Full access and plans are left alone: Ask means a person looks.
- **Git panel** (`gitPanel`, since 9 Nov 2026). Gives every thread whose folder, or one of its projects' folders, is in a git repo a Git panel on the right-hand rail, like VS Code's Source Control: the branch and how far it is from its remote, staged and unstaged files with + and - to stage them, a message box with ✨ to have Haiku write the message from the staged diff, and one button that changes with what's next (Commit, Sync, Publish branch), its chevron for Commit & Push and Commit & Sync. ⌘↩ commits and ⇧⌘↩ commits and pushes. Two chips above the message box, Commit staged & push and Sync, hand the same jobs to the agent instead, and only show when there's something to do. It never force-pushes or skips a hook, and only pushes to remotes you own: your GitHub login, or the owners in runner.json's `gitPanel.pushOwners`.
- **GPUI desktop app** (`gpuiApp`, since 9 Nov 2026). The app in `desktop/`, the one that will run on Mac, Windows and Linux, installed as `~/Applications/Threadbear GPUI.app` beside the Swift app and talking to the same runner. It doesn't do everything the Swift app does yet (`docs/gpui-port/PARITY.md` says what it does), so it's only for someone who wants to try it. Turning this on lets `desktop/scripts/install-app.sh` install it, and makes the runner count it as the app being open when it works out whether you're at your Mac.
- **X search** (`xSearch`, since 9 Nov 2026). Gives every thread's agent, on Claude and Codex, an x_search tool: it asks xAI's Grok to search X and answer, with links to the posts it used and what the call cost. Agents' own web search can't read X, so this is how a thread finds out what people are posting about something, or what an account said. It can keep to some accounts or leave some out, and keep to a range of days. xAI's account filter covers its searches but not every post they bring in, so sources from other accounts are listed apart. It uses an xAI API key of your own (make one at console.x.ai): the first search asks for it in a secret card, and Threadbear keeps it in its secrets folder for every thread after. Each search is billed to your xAI credit, often $0.10 to $0.30 ($5 per 1,000 posts Grok reads, plus its searches and tokens), and each answer says what it cost. If xAI turns the key down, Threadbear forgets it and the next search asks again. What a thread searches for goes to xAI.
- **Prints** (`pages`, since 10 Nov 2026). Diagram Prints take Mermaid source and draw static SVG offline with Pele. Edit Text edits their source and saves a new version; Download includes the Mermaid and SVG. A malformed edit leaves the previous version unchanged. Published diagrams include their source. With Outside agents on, a key allowed to read all can list and read published Prints, never local unpublished ones. Editable CSV sheets are deferred. Lets a thread's agent make a Print you keep (called Pages until 10 Nov 2026): a chart, a dashboard, a report or a doc, from a spreadsheet or data file you give it, a project's files, or a command like the Convex bundle analyzer. Asking again updates the same page to a new version instead of posting another, and the last 10 versions are kept. A page belongs to the thread that made it and can be in any of your projects, or none: a thread pinned to one project puts its pages there by itself. In a reply, a print shows as a card with a picture of it that follows its newest version. Each project's page lists its prints under Prints: click one to open it, and use its menu to Refresh it, Edit with Agent, edit a doc's text yourself, Download it (as files or as a PDF), open or restore an older version, move it between projects, or Delete it (kept 7 days under Recently deleted). Prints are HTML, CSS and pictures with no scripts, unless an agent makes a live one, whose scripts run only after you choose Run them. They're kept on your Mac, in the pages folder in Threadbear's data folder. Nothing about a print goes to Convex unless you choose Publish on it: then its page goes to your own Convex backend, opens on your phone, the website and for anyone with its link, follows new versions, and comes down when you unpublish or delete it. The guide's Prints section lists what to say.
- **Decisions on the Projects page** (`projectDecisions`, since 10 Nov 2026). Every question your threads are waiting on you for, gathered by project. On the Projects page a project's card says how many decisions it has ("3 decisions"), and so does its heading in the sidebar's Projects view. Open the project and its page starts with them: a card for each thread waiting on you, with the thread's title, a line on what it's doing, its questions just as the thread shows them (the Recommended star and Something else too), and Open thread for the whole story. Pick an answer and it goes to that thread exactly as if you'd answered it there: the card says "Sending to" the thread with a spinner, then drops off the list once the thread takes it. A card with several questions sends once each has an answer; with Something else, press Return in its box (⌘Return sends whatever's answered). Nothing new runs and nothing is relayed: each question stays in its own thread. The inbox is as before. Mac app only for now; the phone and the website don't have the page yet.
- **Recap box on quiet threads** (`recapBox`, since 10 Nov 2026). When you open a thread that hasn't done anything for 12 hours or more, a box above the message box says what the thread is for and where it stands, so you don't have to ask. The librarian writes it ahead of time, after each turn, as part of the look it already takes, so it costs no extra model calls. Press × to put it away; sending a message does too. It shows on the Mac, the phone and the website.
- **Run on the card** (`runAsks`, since 10 Nov 2026). When something is yours to run and not the agent's (a production migration, a deploy), the agent can put the command on its card. You see the exact command and the folder it runs in, with a Run button. It runs once, on the machine the thread is on, and the output goes straight back to the agent, so it carries on with no copying or typing "done". Works from the Mac, the phone and the website, except a command the phone or website would show with a secret scrubbed out of it: that one runs only from the Mac app connected straight to the thread's runner. The command can't answer prompts, so one that asks "are you sure?" fails and the agent hears why. It stops after ten minutes.
